## 2. ماذا جرّبنا في هذه الجولة ولماذا

**تشخيص الجولة السابقة** (15/46 بقصّ مثالي): أنماط الفشل كانت كلّها أمراض CTC: خانات ساقطة (`0619.54` بدل `006719`)، دمج الكسور الصغيرة
مع الرقم (`00533788.2`)، وثقة عالية على الخطأ (23091). الكاشف لا يعاني منها لأن كل رقم كائن له صندوق وارتفاع ودرجة.

**ما بنيناه:**
1. `lab/synth2.py`: مولّد مشاهد كاملة (خلفية → جسم عداد → شاشة → سطر رئيسي + أسطر ثانوية A/V/Hz + كسور صغيرة بنقطة أو بدونها + مقاطع شبحية +
   أرقام مطبوعة (رقم تسلسلي/موديل) **كأمثلة سلبية** + باركود + كتابة يد عربية + لوحات 2×2 حتى 5×3 + وهج فلاش + ضبابية حركة + منظور ±12% + دوران
   حتى ±35° + JPEG 30–92). تسميات: صندوق لكل رقم (0–9)، النقطة العشرية (10)، وسطر القراءة الرئيسي (11).
2. `lab/det_model.py` **DigitNet**: شبكة CenterNet خفيفة (213k معامل، ~840KB ONNX لكل نموذج، **المجموع 1.7MB**)، إدخال NHWC بقيم 0–255 والتطبيع
   داخل الرسم البياني (كي يطابق Android بالضبط)، وNMS داخل الرسم البياني. نموذجان من نفس الكود:
   - **المحدِّد** (256×256 على مستطيل القارئ): فئة واحدة = سطر القراءة الرئيسي.
   - **القارئ** (64×448 على قصّ السطر): 11 فئة.
3. `lab/assemble.py` ⇄ `ReadingAssembler.kt`: تجميع هندسي **قابل للقياس** (دمج عبر الفئات مع الاحتفاظ بالبديل، تجميع أسطر، اختيار أطول سطر، قطع
   الكسور عند النقطة أو عند هبوط الارتفاع < 0.8، فحص انتظام المسافات → `MISSING_DIGIT` بدل التخمين). عشر حالات اختبار متطابقة في Python وKotlin.
4. ثقة «أمينة»: الخانة غير مؤكدة إذا درجتها < 0.45 أو كان لها بديل بدرجة ≥ 50% منها. القراءة «واثقة» فقط إذا كل الخانات مؤكدة **و**البنية سليمة.

**ما لم نجرّبه ولماذا:** PARSeq-tiny (محوّل؛ يحتاج نفس البيانات الحقيقية التي لا نملكها ويكرّر عيب القراءة الشمولية)، ML Kit على السندبوكس (لا
يعمل على لينكس — موجود في التطبيق).

## 4. المخاطر
- الفجوة اصطناعي→حقيقي هي الخطر الأول؛ علاجها المباشر: 300–1000 صورة معتمدة من النظام بصناديق أرقام (خطة التحسين في `benchmark_report.md`).
- شاشات SMART MT10 الباهتة جداً و TAGADOD ذات المقاطع الشبحية الزرقاء: حتى العين تحتاج تحسيناً؛ المولّد يحاكيهما لكن بلا ضمان.
- أزمنة الجوال غير مقاسة في السندبوكس؛ التطبيق يقيس كل مرحلة ويكتبها في CSV.
