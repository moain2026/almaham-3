# Consultation brief — almaham-3 meter reader (2026-10-21)

## System (what exists)
Offline Android app reads Yemeni electricity meters (LCD, seven-segment). Pipeline on the phone (ONNX Runtime minimal, 7.7 MB APK):
1. User draws a loose rectangle around the WHOLE meter (owner wants this; the meter body is archived).
2. LINE LOCATOR: CenterNet-lite (213k params, stride 4), input 256x256 letterbox of the crop, 1 class = "main reading line" (tight box of integer digits). Top peak -> box, padded 18% x / 45% y.
3. DIGIT READER: same backbone, input 64x448 letterbox of the padded line crop, 11 classes (0-9 + decimal dot), outputs per-digit boxes.
4. ASSEMBLER (rule-based, Python/Kotlin mirror): sort digits by x, decimal boundary = first dot between digits OR first digit whose height < 0.65 x median OR (if >=7 regular cells) cut at 6; large gap splits numbers. Output = INTEGER part only (no decimals) — the business requirement.
Training: ~400-500 real line crops with weak digit boxes (from the current locator+reader, accepted only when the reader's digit count equals the human-verified text length), 50/50 with synthetic seven-segment scenes; strong augmentation; AdamW; CPU only (no GPU).

## Meter types (6+ types, all Yemeni field photos, phone cameras, flash, glare, tilt, handwriting on housings)
- TOMAS_SMART / TOMAS_STATIC: 6 integer cells, 2 SMALLER decimal cells, dot. Works well (6-7/7).
- TAGADOD: 6 cells + 1 small decimal. OK (5-6/7).
- EMETER_GREEN: green PCB visible behind glass, 6 integer + 2 decimals SAME height, dot faint. 1/6.
- CRYSTAL: large digits, 2-4 integer cells + 2 decimals SAME HEIGHT, dot nearly invisible, blank leading cells, secondary small line below (V/A/kW), "kWh" printed right after decimals. 0-2/7.
- SMART_MT10: dark LCD on yellow housing, often very faint. 0/1.
- NEW today: CHINT 3-phase (digits on a black LCD band, reading line is above a blue label with another number), HPL 3-phase (5 int + 1 dec, 'W' unit right after), DDS-type.

## Measured numbers (honest)
- 49-photo set (owner-verified v3, 39 readable): rectangle 14-16/39; whole photo 14-16/39.
- Frozen human test set (34 ERP photos, whole photo): best 17/34 (new locator today). CRYSTAL 2/7, EMETER 1/6, OTHER 0/4.
- Oracle-crop reader on held-out verified val (105): 82/105 exact; among <=4-digit (Crystal-like) 0/9.
- Fraction cell height / integer cell height on 498 real crops: median 0.99, p95 1.15 -> height rule is blind.
- Dot class peak on Crystal: 0.07-0.29 (threshold 0.30) — the dot is ~1px after downscale.
- In-plane tilt tolerance measured: ~±10 degrees.
- Locator self-training trap found: training shards only include photos the CURRENT locator already finds (acceptance requires locator success), so it never learns its own failures. Today built text-supervised localisation (slide the reader over windows, accept the window whose text == human label): 62% of verified photos located, 25/25 visually correct in a pilot.

## Constraints
- Must run offline on mid-range Android, < 0.5 s total, model < ~10 MB. ORT minimal build currently supports 16 ops (conv, relu, add, maxpool, resize, sigmoid, ...); adding ops is possible but costs APK size.
- No GPU for training (4-core CPUs x2). ~500 verified photos now, +~100/day from owner. Can collect box/corner labels if a labelling UI is built (owner willing).
- No AGPL (Ultralytics YOLO excluded). Python and Kotlin must stay literal mirrors.
- Goal as the owner phrases it: "0.0 error". We interpret as: zero confident-wrong, >=99% exact on accepted, reject the rest to manual.
