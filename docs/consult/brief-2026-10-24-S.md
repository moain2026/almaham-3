# Brief for external consultation — almaham-3 meter reader (agent S, 2026-10-24)
No customer images are included; only aggregate numbers and code facts.

## Product & constraint
Offline Android app reads the INTEGER part of electricity-meter LCD displays (Yemen). User draws a rectangle around the whole meter; app must find the reading line and read it. Owner's hard rule: **"0.0 error" = never output a wrong number with confidence; when unsure leave the field empty** (selective prediction). Secondary: maximize coverage. No AGPL. Must run on phone CPU in <100 ms; current models are two tiny CenterNet-style nets (0.21M params each, stride-4 heat-map + wh + offset), ONNX Runtime.

## Pipeline (facts)
1. LOCATOR (input 256×256 letterbox of the meter crop; 1 class LINE = union of integer digit boxes) → best peak → padded line crop.
2. READER (64×448 letterbox of line crop; 11 classes = digits 0-9 + decimal dot) → detections → `assemble.py`: cross-class NMS keeping runner-up as `alt`, group into lines, decimal boundary = first dot between digits OR first digit with height < 0.65 × median OR cells beyond 6 in a regular lattice, pitch regularity check (MISSING_DIGIT if gap > 1.75 × pitch).
3. Confidence: per-digit peak score; reading `min_conf` = min over digits. Current candidate gate: `status==OK & min_conf≥0.55 & all(alt<0.5×score)`.

## Data (facts)
- Train: 498 line crops from old labels (ft6) + 531 whole-meter crops with human-verified readings (m3; agent D; 85/15 split by photo key, NOT by meter id). Owner_visual samples weight ×2. Types in m3: CRYSTAL 98, SMART_YELLOW 56, KENWELL 39, TAGADOD 103, OTHER 66, TOMAS_STATIC 53, TOMAS_SMART 113.
- 612 further human-labelled photos exist but were NOT used: the automatic weak-labeller (text_locate = run reader over sliding windows, accept if digit string matches label) failed to localize the line. Of these: TOMAS 176, SMART_YELLOW 96, CRYSTAL 74, OTHER 37, MECHANICAL 34, TAGADOD 24.
- Synthetic: 24k rendered seven-segment lines (line_s1) + 3k Crystal-style (line_crystal_opt2: fraction digits same height as integer, dot ~1px). 50/50 real/synthetic per batch.
- Frozen evaluation (never trained on): 49 owner photos (39 readable; mode A = user rectangle, mode B = whole photo) + 34 ERP photos by type ("TH34"). Also 97 owner field photos from the web demo with feedback.
- Training: AdamW 2e-4, cosine, 3000 steps, batch 32 (reader) / 24 (locator), AUG v2 (affine ±10°, photometric, blur, JPEG, digit permutation), focal loss (CenterNet) + L1 wh/off, CPU only (4 cores sandbox + 4 cores VPS). ~50 min/reader run on 1 core.

## Measured results (literal)
Best deployed: locator_m1 + reader_ft6m2_s1 → 49: A 22/39, B 19/39; TH34 21/34 (TOMAS 7/7, TAGADOD 7/7, OTHER 2/4, EMETER/SMART_YELLOW 2/6, CRYSTAL 2/7). Strict gate on 73 images: 17 accepted / 0 wrong (coverage 23%). Gate min_conf≥0.45: 33 correct / 5 wrong of 38.

**Seed study (same recipe, different seeds, 3 days of autotraining):**
- Locator retrained on m3 (n=27 seeds): TH34 23.0±1.3 (all ≥21), B 20.3±1.7, A 21.3±1.7. BUT strict gate: mean 1.37 wrong accepted (range 0–4); only 4/27 seeds have 0 wrong. The better locator admits more images into the "confident" region and some are wrong.
- Reader retrained on ft6m3 + Crystal synth (n=31 seeds): TH34 19.8±0.6; **CRYSTAL 2/7 in 31/31 seeds**. Synthetic Crystal data moved nothing.
- Weight averaging (uniform soup) of locator seeds: soup5 → A24/B20/TH34 24, gate 14/0; soup10 → 23/20/21, gate 16/3; soup27 → 23/21/23, gate 17/1. Non-monotone in N.
- Held-out val of m3 (68 images) gives locator IoU50 66/68 for EVERY seed → useless for model selection.

**Failure taxonomy of best model on the 73 frozen images (status OK but wrong):**
- EXTRA_RIGHT (+1 digit appended = fraction read as integer): 6 (4 Crystal, 1 Tomas, 1 Other). Line score 0.27–0.47, min_conf 0.32–0.53.
- ONE_DIGIT_SWAP (ghost segment confusions 5→6, 9→0, 9→8, 2→3, 7→1): 5. **line_score 0.51–0.74, min_conf 0.34–0.59 — these pass or nearly pass the gate.**
- MULTI_DIGIT_SWAP: 4. OTHER (wrong line / garbage): 10, min_conf 0.18–0.37, line_score 0.30–0.58.
- MISSING_LEFT (leading digit dropped, e.g. 007022→22): 2.
- Separability on 49B: line_score median OK 0.61 vs wrong 0.51; min_conf median OK 0.53 vs wrong 0.35.
- Root cause doc for Crystal: fraction digits have the SAME height as integer digits (height ratio median 0.99), dot is ≤1 px after downscale (peak 0.07–0.29, below 0.30 threshold). Geometry rules cannot carry the information. A previous consultation rejected "fixed K digits per meter type" (unsafe: Crystal has no leading zeros, type errors are systematic).

## Questions (answer each concretely, with numbers/thresholds and literature; say "unknown" if unknown)
Q1. **Selective prediction gate**: Given the signals we have (per-digit peak, runner-up margin, locator line score, lattice regularity, number of digits, optional TTA agreement), what is the best-practice way to build a gate that achieves ~0 wrong among accepted while maximizing coverage, given only ~73 frozen eval images + ~68 held-out val + 97 field photos? Should we fit a small logistic model on held-out data (which features), or use conformal prediction (which score, which calibration set), or a rule? How do we validate it honestly with so few images (Clopper-Pearson bounds)?
Q2. **Integer/fraction boundary** for Crystal-like displays where the fraction is same-height and the dot is invisible: rank concrete options: (a) add a 12th heat-map class "last integer digit" trained from labels (we know N = len(label)); (b) a per-line 1-D boundary regressor head; (c) read at 2× resolution (128×896) so the dot survives; (d) sequence model (CTC) with the boundary as a token; (e) meter-type classifier → digit count prior with uncertainty. For each: expected gain, risk of confident errors, data needed, CPU cost.
Q3. **Using the 612 unlabelled-localization photos**: the human reading is known but the line box isn't. Options: (i) widen the weak-labeller (lower threshold, more windows, multi-scale); (ii) train the locator with image-level supervision (MIL / "reading-consistency" loss: pick the candidate line whose reader output matches the label); (iii) pseudo-label with the current locator and accept when reader output == label (self-training with hard verification); (iv) manual boxes. Which gives the most reliable boxes without poisoning? Any known pitfalls?
Q4. **Ghost-segment confusions** (5↔6, 9↔0/8, 2↔3, 7↔1) on LCDs with visible off-segments: which training/data changes reduce them (segment-level auxiliary head predicting 7-segment mask? contrast-normalised input? hard-negative mining of off-segments in synthetic data? type-conditioned augmentation)? Do you know published results for seven-segment OCR with ghosting?
Q5. **Model selection with noisy tiny eval sets**: with 27 seeds giving TH34 21–25, how should we pick a model to deploy without overfitting to the 73 frozen images? Weight averaging / SWA / EMA? Ensembling two seeds at inference (2× cost)? Report which is standard practice for small detectors.
Q6. **Training efficiency on 8 CPU cores total**: current 1 step (batch 32, 64×448, 0.21M params) ≈ 0.4 s on one core; data pipeline 0.03 s. Any concrete wins (channels_last, torch.compile on CPU, larger batch fewer steps, mixed precision is slower on this Xeon) — or is this already near the floor and we should spend cores on more seeds/longer schedules?
Q7. Anything in our setup that violates standard practice and would make our numbers untrustworthy (e.g. split by photo key instead of meter id; selecting on the 49/34; 50/50 real/synth ratio; val set that saturates)? Be blunt.
