## 1) Decimal boundary when fraction cells are same height (Crystal / Emeter / HPL)

### Ranking (most reliable under your constraints → least)
**1) (d) Meter-type classifier → fixed integer-cell count per type (with a “short/variable-length” override for Crystal)**  
**Why:** Decimal-dot is often <1 px after downscale (you measured 0.07–0.29 peaks) so “detect the dot” is structurally brittle. Many deployments solve decimals by **meter-type priors** because the integer length is dictated by the register format, not by image cues. With ~500 photos you can get a robust **6–10 class type classifier** quickly on CPU.  
**How to handle Crystal (variable 2–4 integers):** don’t “fix” Crystal to a single length; instead combine type with a **blank-leading / variable-length rule**: parse all detected digits, then take **the longest left-aligned run before the unit glyph zone**, or enforce **max integer digits** (e.g., 4) and allow fewer if leading cells are blank.  
**Failure modes it fixes immediately:** HPL “237464” (fixed: 5 int + 1 dec), Emeter fixed format, most Tomas/Tagadod.  
**Cost:** tiny MobileNetV2-0.35-ish classifier is <100k params; input can be your already-cropped meter-body rectangle (step 1).

**2) (b) Tiny sequence head (CTC) that emits explicit boundary token (or emits integer-only text directly)**  
**Why:** If you treat this as “read the integer register only” rather than “detect digits + dot”, you avoid the dot entirely. CTC is used widely in OCR because it tolerates missing separators and variable spacing. With your ORT-op constraints: CTC decoding itself is fine on CPU, but implementing a good feature extractor + sequence model with only your allowed ops is the gating factor. If you can add **Softmax + LogSoftmax + Gather/ArgMax** ops, it’s viable.  
**Concrete design:** small CNN → 1D time axis (width) → per-timestep logits over {0–9, blank, boundary}. Boundary token placed between integer and decimals during training; at inference you stop at boundary and output integer.  
**Data reality:** You already have text labels; you *don’t* need digit boxes. Your new “text-supervised localisation” is exactly the right direction for this.  
**Risk:** engineering + ORT operator additions; calibration of “reject” needs care.

**3) (a) Extra heatmap class “last integer digit” supervised from text length**  
**Why:** This is compatible with what you have (CenterNet-style peaks). Supervision is easy if you know the integer length for that meter type or for the human label. But for Crystal variable length + blank leading cells, “last integer digit” may be ambiguous when detections are missing or merged.  
**Still useful:** As a *second signal* combined with type prior, not as the only mechanism.

**4) (e) Higher input resolution so dot survives (96×672 etc.)**  
**Why:** It helps dot visibility *sometimes*, but it will not fix: faint dots, glare, LCD polarization, and cases where dot is physically absent or printed weirdly. It also increases runtime and makes the digit detector’s job harder (more texture, more false positives like “kWh”).  
**Use only if:** you keep a strict reject policy and only use dot as confirmation, not as the decision-maker.

**5) (c) Per-cell integer/decimal classifier using position-from-right + neighbor glyphs (“kWh/W”)**  
**Why it ranks low:** it presumes you have stable “cells”. Your system is box-per-digit with variable counts and clutter (“kWh”, secondary lines). Cell assignment becomes the hard part. Also the neighbor glyph cue (“kWh/W”) is unreliable under blur/glare and language/print variations.

### What I would do for boundary, concretely
- Implement **type classifier (d)** first, because it immediately fixes HPL/CHINT-style “fraction kept” errors at near-zero compute cost.
- For Crystal/Emeter where dot is faint and formats vary, push toward **CTC integer-only reading** as the medium-term solution. If you can’t add ops, do (a) “last-integer heatmap” + type prior as an interim.

### What I would NOT do
- **Not rely on dot detection as primary boundary** (your measured dot peak + downscale makes it mathematically fragile).
- **Not keep the height-rule** for decimals (you already proved median ratio ~0.99; it’s blind).

## 2) Locator distracted by printed serial labels / blue labels / top-right “kWh” region

You’re seeing the classic failure of “single-class detector on a cluttered crop”: it will lock onto any digit-like texture. Hard negatives help but won’t eliminate “No. 2022-…” cases because the visual statistics are too similar.

### Recommended approach (minimal change, high leverage)
**(b) Add a “display/LCD region” class to the same locator net + enforce reading-line must be inside display**  
- Train two classes:
  1) **display box** (or quadrilateral corners if you can)
  2) **main reading line box**
- Inference: pick best display; then search reading-line peaks **only within display ROI** (or run line locator on the display crop only). This alone kills cases A/D/E where it jumps to printed labels.

This is the smallest architecture change that directly addresses your distractors without a heavy cascade.

### If you can label corners: do corners, not just boxes
For glare/tilt and the CHINT “band above blue label”, a quadrilateral is better than a box.

**Minimal <300k-param corner+legibility architecture**  
- Backbone: your current lite backbone (keep it).
- Heads:
  - **4 corner heatmaps** (top-left, top-right, bottom-right, bottom-left) at stride 4 (64×64 for 256 input).
  - **corner offset** regressions (dx, dy) per corner (standard CenterNet trick).
  - **legibility score** scalar (global average pool + 1×1 conv).
- Params: the heads are tiny; total stays in the ~200–300k range depending on channels.

This is basically “CenterNet for corners”. It’s not CDCC-Net, but you can approximate the useful part (corners + quality) within your ops budget.

### Geometric prior (c)
Useful as a *constraint*, not as a detector:
- Inside predicted display quad, compute horizontal projections / connected components on a binarized image → pick the densest seven-seg row.  
But I would not bet production accuracy on handcrafted projection under glare/polarization; use it only as a fallback to reject bad crops.

### (a) Full cascade meter-body → LCD → reading line
I would **not** start with a full 2–3 stage cascade unless you’re forced to by extreme variety, because it increases failure modes: if stage 1 misses, everything misses. Your step (1) already gives meter-body, so you’re halfway there; add **display detection** next, not another meter-body detector.

### What I would NOT do
- **Not keep a single “reading line” class** with no notion of “this is inside a display”. That’s exactly why “No. 2022-…” wins.
- **Not try to solve distractors only via hard negatives**; it becomes an arms race and still won’t encode the structural constraint “reading is inside LCD”.

## 3) Confidence / rejection (zero confident-wrong, accept-only-when-sure)

You need **calibrated “probability of exact match”**, not “average digit score”.

### A concrete, production-style confidence recipe (works with detectors)
Compute multiple signals, then learn a tiny calibrator (logistic regression / small MLP) on held-out data.

**Per-candidate features (examples that matter in meters):**
1) **Digit count consistency**: does count match expected integer length for meter type (or plausible range for Crystal)?
2) **Min/mean of per-digit peak scores** (but don’t use product; it collapses too fast with length).
3) **Spatial sanity:**
   - median digit width/height; stddev of widths (flags “kWh” contamination)
   - line straightness: y-centers variance after sorting by x
   - overlap / gaps: large unexpected gaps often mean a missing digit or split.
4) **Crop quality / legibility score** from your locator (section 2).
5) **Stability under small perturbations**: run 3–5 quick TTA passes (±5° rotate, slight scale) and measure:
   - exact string agreement rate
   - per-position agreement (Levenshtein distance)
This is extremely effective for rejecting borderline glare/partial crops like case B/E. With small models, 5 passes can still fit in <0.5 s if you only rerun the **digit reader** on the same line crop.

**Calibrator:**
- With ~100 held-out photos you can fit:
  - **Platt scaling / logistic regression** to predict `P(exact)` from the above features.
- Pick an operating point like: accept only if calibrated `P(exact) ≥ 0.995` (tune to “0 confident-wrong” on held-out; expect high reject rate initially).

**“Checksum with previous reading”**
Good as an additional *business rule* (monotonic non-decreasing, max daily delta), but it’s not a substitute for visual confidence. Use it to **force reject** when violated, not to accept.

### What I would NOT do
- **Not use “product of digit probabilities”** as confidence; it is length-biased and poorly calibrated.
- **Not accept based on a single threshold of min digit peak**; it misses structured failures (wrong region, “kWh” glyphs, extra fraction digit).

## 4) Training on CPU with ~500 real + synthetic (what actually moves the needle)

### Biggest needle-movers in your situation
1) **Fix the sampling bias / self-training trap (you already discovered it)**
   - Your new text-supervised localisation is the right fix.
   - Make sure your training set includes *failed-locator cases* by design. If the locator never sees them, it never learns them.

2) **Rebalance by meter type and failure mode**
   - Oversample Crystal/Emeter/MT10/3-phase types heavily (e.g., 3–5×) even if it hurts aggregate loss. Your KPI is worst-type accuracy.
   - Use **type-conditioned augmentation**: Crystal gets glare bands + partial occlusion + “kWh” near digits; Emeter gets faint dot/no dot; MT10 gets low-contrast + LCD bleed.

3) **Loss / label strategy**
   - For CenterNet-style heads: use **Gaussian heatmaps** (CenterNet / TTFNet-style) with radius tied to object size. TTFNet (Zhou-style dense supervision) often helps small objects like dots, but again: don’t bank on dots.
   - Add **IoU/DIoU loss** if you can (op constraints may block). If not, keep L1 but increase box regression weight for the locator.

4) **EMA + longer schedule**
   - EMA of weights (0.999) helps stability on small datasets.
   - Longer training with strong aug usually helps more than fancy tricks; CPU cost is time, but you can run overnight.

5) **Pseudo-label refinement loops (careful)**
   - Only pseudo-label when you have **high precision gating** (e.g., text match + high stability under TTA).
   - Do *not* expand labels from “model agrees with itself”; expand from “model matches human string under diverse crops” (your window-scan idea).

### What I would NOT do
- **Not do multi-round pseudo-labeling without a precision gate**; it will reinforce the current failure modes (you already lived this).
- **Not spend time making synthetic more realistic instead of collecting targeted real failures**. 100 real Crystal/Emeter/MT10 hard cases beat 10k synthetic.
